# 01 仓库布局

## 适用范围

本文件规定采用本框架的仓库里，顶层目录如何划分、一个新文件应当落在哪里、以及谁有权改动某个目录。它约束的是位置，不约束内容。规则编号形如 `L-01`。

本文件不规定业务代码的内部目录结构；那属于各仓库自身的架构决定。

## 1 顶层目录

一个采用本框架的仓库有四个受本规范约束的顶层位置：

| 目录          | 内容                       | 谁改动它         |
| ------------- | -------------------------- | ---------------- |
| `docs/`       | 规范、ADR 与说明性文档     | 规范作者         |
| `tools/`      | 门禁与构建工具的执行逻辑   | 工具作者         |
| `governance/` | 门禁读取的配置与基线数据   | 规则作者与评审者 |
| `tests/`      | 与源文件一一镜像的测试用例 | 该源文件的作者   |

- **L-01**　新增一个受本规范约束的顶层目录之前必须先有一份状态为已接受的 ADR；直接创建的顶层目录禁止被后补追认。[[review]]
- **L-02**　一个新文件的归属按「谁产出它」判定：由命令确定性产出的写入生成物目录，由人手写且被工具读取的写入 `governance/`，可执行的检查逻辑写入 `tools/`，规范文本写入 `docs/`。[[review]]

## 2 生成物与手写物的分界

- **L-03**　生成物禁止被手工编辑；修正生成物的唯一方式是修正产出它的命令并重新运行。[[review]]
- **L-04**　门禁的执行逻辑与它所依据的数据必须分居两个文件：逻辑在 `tools/`，数据在 `governance/`。禁止把某个具体仓库的文件清单、路径、计数编入工具源码。[[machine]]
- **L-05**　`governance/` 下的数据文件禁止由工具自动重写。它是人手维护的输入，一旦能被一条命令再生，「重新生成一次」就成了接受新违规的捷径。[[machine]]

L-04 与 L-05 看似相反，实际互补：L-04 把数据赶出代码，L-05 阻止数据退化成代码的输出。基线棘轮的完整理由见 `07-BASELINE-RATCHET.md`。

## 3 不可再生材料

- **L-06**　不可再生的材料——原始采集数据、外部交付物、只此一份的记录——禁止存放在任何会被重建流程清空或覆盖的目录。[[review]]
- **L-07**　每个受本规范约束的目录必须在 `docs/` 下有唯一一份说明它存在理由的文档；无人认领的目录必须删除或被认领。[[review]]

## 4 路径的书写

- **L-08**　文档中引用仓库内路径时必须使用相对于仓库根的正斜杠路径，并置于反引号内；禁止使用绝对路径与主目录相对路径。[[machine]]
- **L-09**　目录引用必须以 `/` 或 `/**` 结尾，使它与同名文件的引用可区分。[[review]]

## 变更影响

修改第 1 节的目录表会改变 `governance/spec-consistency.json` 的 `resolveRoots` 与 `documentRoots`，两者必须同一次修改。修改 L-04 或 L-05 会使 `tools/verify-gate-baselines.mjs` 的设计前提失效。
